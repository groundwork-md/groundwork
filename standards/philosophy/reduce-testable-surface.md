---
title: "Reduce the testable surface before testing it"
type: "rule"
category: "philosophy"
---

Every hand-written line is a line that can be wrong and must be tested. Before writing tests for a
surface, ask whether the surface needs to exist — a mature library, a generated artifact, or a
declarative table removes whole classes of defect rather than catching them.

This is not about writing less code for its own sake. It is that **repetitive plumbing is where
defects hide**: it looks obviously correct, it is tedious to test, and it is exactly the kind of
thing a reviewer's eye slides over.

**Why:** one command-line tool's command layer was ~600 lines of hand-written `argparse` wiring, with the
same shape repeated per command: declare a subparser, add flags, dispatch, build a payload, render.
Four defects shipped in that layer at once (`[[derive-tests-from-the-code-surface]]`), all of them
argument-passing mistakes in code that looked right. A declarative command table with generated
parsing and dispatch would have made three of the four **unrepresentable**, not merely detectable.

The same project got this right elsewhere and it paid: the command reference is *generated by
walking the real parser*, so documentation drift is impossible rather than policed — and a test
regenerates it and compares. That is one defect class that simply cannot occur.

**How to apply:**

1. **Prefer a mature library to hand-rolled logic**, subject to your layer's dependency-license policy and
   `[[prefer-self-hosted-fewer-third-parties]]`. A dependency is surface too — but a well-tested
   dependency has had its surface tested by more people than this project ever will.
2. **Generate what can be generated**, and test the generator once instead of its output many
   times. Reference documentation, serialisers, client code from a schema, dispatch tables. Then
   assert the generated artifact matches its source, so drift fails a test.
3. **Prefer declarative data to repeated code.** A table of commands, routes, states or fields that
   something walks is one thing to get right; the same shape written out N times is N chances to
   get it wrong, and the N+1st is the one that ships.
4. **Count the repetitions.** Three near-identical blocks is the signal to replace them with a
   table and a loop, not to write a third test.
5. **Where surface cannot be removed, make it enumerable** so a completeness guard can walk it.
6. **Do not trade a real dependency for a fake one.** Pulling in a large framework to avoid twenty
   lines is not a reduction — it moves the surface somewhere less visible. The test is whether the
   defect class disappears, not whether the line count does.

Applies regardless of language or project. Complements `[[prefer-composable-over-bundled]]` and
`[[prefer-maintainability-audits]]`.
